> **Tipo:** revisão rápida de evidências (não é revisão sistemática PRISMA).
> **Escopo:** o que muda decisões deste repositório (Julia/Agents.jl + Python
> de análise + demo HTML/JS), não um survey exaustivo.
> **Regra:** cada claim externa tem fonte, data/versão e escopo. Números do
> paper continuam governados por `verificação número-a-CSV (privada)`; nada aqui altera
> claims do manuscrito. Preprint é marcado como preprint.

## 1. Pergunta

Como elevar a qualidade de código científico/ABM sem transformar cobertura em
teatro, golden em carimbo e teste flaky em `retry`? Em particular: qual é o
oráculo de um ABM estocástico, o que deve ser gate de PR e o que deve ser
gate de release?

## 2. Método

- **Queries:** research software testing survey; metamorphic testing scientific
  software; flaky tests survey; mutation testing LLM; agentic software
  engineering benchmarks; Julia Aqua/JET/ExplicitImports/AllocCheck;
  property-based testing Julia; Node test runner; SLSA.
- **Critérios:** fonte primária (DOI/arXiv/docs oficiais), data 2025–2026
  quando o tema muda rápido, aplicabilidade direta ao repo.
- **Limitação:** fotografia de 2026-11-06; ferramentas e versões envelhecem.
  Não é uma revisão de literatura completa; claims marcadas como preprint
  não são peer-reviewed.

## 4. Consenso / emergente / controverso / hype

- **Consenso:** o problema do oráculo é central em software científico;
  cobertura sozinha não mede força de teste; flaky tests destroem confiança;
  CI em camadas é melhor que “rodar tudo em todo commit”.
- **Emergente:** metamorphic testing como técnica de primeira linha para
  simulação; mutation testing assistido por LLM; avaliação de agentes com
  held-out e restrições de review; tooling Julia de qualidade (Aqua,
  ExplicitImports, Supposition).
- **Controverso:** substituir revisão humana por testes gerados por LLM;
  formalização estilo SpecGuard em projetos pequenos; exigir SLSA alto para
  artefato de pesquisa.
- **Hype:** “100% de cobertura = qualidade”; “o agente passou nos testes,
  então está pronto”; “mais testes sempre é melhor” (sem orçamento e sem
  oráculo).

## 5. Implicações para o repo (backlog)

### P0 — antes de novo claim de qualidade
1. Criar a skill `scientific-software-testing` (feito) e tornar explícito o
   contrato de teste: spec → risco → oráculo → seed → asserção → artefato.
2. Formalizar as relações metamórficas já usadas (quantização ε, conservação,
   invariantes de região, inertização) e adicionar as que faltam (simetria,
   `absorbed_at`, barreiras, scheduler).
3. Manter testes held-out/hidden para mudanças feitas por agentes; nenhum
   agente pode editar teste/gate para passar sem revisão e justificativa.
4. Política de flaky: nada de retry até verde; quarentena com issue, data,
   seed e comando de reprodução.

### P1 — qualidade e reprodutibilidade
5. Adotar Aqua.jl e ExplicitImports.jl como checks de teste quando o custo de
   dependência for aceitável; começar sem gate bloqueante.
6. Testar a demo `apresentacao/axelrod.html` com `node --test` (funções puras
   + smoke + e2e mínimo), sem `jsdom`; usar `node:vm`/DOM mínimo.
7. Ampliar `scripts/mutation.py` para os mecanismos novos (fadiga, treino,
   auditoria, shift/turnover) e manter ≥70% de não-equivalentes.
8. Separar testes estatísticos (ensemble/IC/poder) dos testes rápidos; rodar
   no nightly/release, não no PR.

### P2 — quando houver upgrade/artefato
9. JET.jl e AllocCheck.jl só depois de subir Julia para uma série compatível
   (JET v0.13 exige 1.12+; repo em 1.10.8).
10. Proveniência de release: checksums, `CITATION.cff`, `.zenodo.json`,
    commit/tag e lock; SLSA completo só se houver distribuição binária.

## 6. O que mudaria a decisão

- **Julia 1.12+** no núcleo: reabrir JET v0.13 e AllocCheck como gates.
- **Aqua/ExplicitImports** causarem conflito de dependência ou ruído:
  manter como job não bloqueante e documentar.
- **Demo virar produto web** com browser real: aí sim avaliar Playwright/
  Cypress; para o artefato standalone, `node --test` basta.
- **Agente passar a editar testes/gates**: endurecer G1 e adicionar revisão
  obrigatória de diff em `test/` e `scripts/check_gates.py`.
